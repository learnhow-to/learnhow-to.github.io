The Problem

Japan's strict 2024 overtime regulations (2024年問題) put extreme operational pressure on civil engineering contractors. Yet, field sites remain heavily dependent on paper daily logs (作業日報). Foremen spend 15–30 minutes handwriting crew rosters, excavator hours, and fuel consumption in dusty or rainy conditions, while back-office staff spend days manually transcribing slips into Excel.

  • Subterranean excavation pits and tunnel blackspots cause standard web apps to drop unsubmitted reports.
  • Over 90% of daily workers, heavy machinery, and tasks are identical, yet laboriously re-written every morning.
  • Carrying physical wooden chalkboards and tripods into muddy trenches slows down photo inspections required by MLIT (国土交通省).
  • Month-end CSV exports corrupt Japanese Kanji characters (mojibake) in Microsoft Excel for Windows.

The Solution

An industrial-grade, offline-first dual-interface B2B SaaS platform engineered for an enterprise civil engineering contractor in Tokyo (Confidential Client). Utilizing browser IndexedDB with Optimistic Concurrency Control (HTTP 409) and idempotent sync queues, it enables field foremen to complete daily reports in under 30 seconds via intelligent previous-day cloning (前日コピー), generates MLIT-compliant digital inspection chalkboards directly on photos via HTML5 Canvas (電子黒板), and provides a 3-tier digital Hanko (電子印鑑) approval workflow.

The Problem

  • Repetitive manual entry of terminal ADB commands (app restarts, cache clearing, permission toggles).
  • Pushed files end up in deep directories where native gallery apps fail to index them without a device restart.

Technical Case Study

Detailed breakdown of architectural decisions, engineering constraints, trade-offs, and verified local benchmark measurements.

1. Context, Constraints & Goals

When testing Android software on physical hardware, an engineer frequently switches context between three windows: the code editor, the terminal running ADB commands, and the physical handset screen.

Constraint Requirement Reason
Host Resource Footprint Keep total RAM consumption ≤ 120 MB Allows the tool to run continuously alongside heavy IDEs without degrading host system performance.
Mirroring Responsiveness Low-latency 60 FPS video & keyboard/mouse passthrough Manual test iterations require immediate tactile feedback.
Thread Safety Zero GUI freeze during ADB I/O Subprocess timeouts or slow network ADB calls must not block the Qt event loop.
Android Storage Sync Immediate Gallery indexing for transferred media Avoids manual reboots or app restarts after pushing test assets.

2. Architectural Decisions & Trade-offs

DECISION A

PySide6 (Qt6) over Electron / Webview

Choice: Built as a native desktop application in Python 3.12 with PySide6.

Rationale & Trade-off: Electron wraps a full Chromium runtime and Node.js process, typically demanding 250–500 MB of RAM before running application code. PySide6 starts cleanly in under 45 MB of RAM and integrates directly with OS-level subprocesses and threading primitives. The trade-off is higher styling discipline compared to CSS flexbox, but memory efficiency was prioritized.

DECISION B

Delegating Video Stream to scrcpy Engine

Choice: Orchestrating external scrcpy process instead of building a custom C++ H.264 decoder.

Rationale & Trade-off: scrcpy has over seven years of active optimization by Genymobile, utilizing device-native Android MediaCodec hardware encoding. Re-implementing a custom decoder inside Python would introduce unnecessary CPU decoding latency and stability risks. Orchestrating scrcpy via managed subprocess flags allows the application to leverage mature hardware acceleration while focusing engineering effort on the testing workflow layer.

DECISION C

High-DPI Coordinate Handling via Win32 API

Choice: Integrated ctypes.windll.user32 to calculate physical device pixels.

Rationale & Trade-off: Modern Windows laptops use 125% to 200% DPI scaling. Passing raw logical Qt window coordinates to external window wrappers caused the mirrored display to render in a quartered or distorted frame. Multiplying by devicePixelRatioF() and issuing SetWindowPos with SWP_FRAMECHANGED forced an SDL surface resize, guaranteeing crisp, pixel-perfect rendering.

DECISION D

Scoped Storage & Broadcast Synchronization

Choice: Implemented MIME-type routing and automated MEDIA_SCANNER_SCAN_FILE broadcasts.

Rationale & Trade-off: On Android 10+ (API 29+), raw byte writes to /sdcard/Download/ remain invisible to the native MediaStore content provider until indexed. By routing images to /sdcard/Pictures/, videos to /sdcard/Movies/, and broadcasting intent scans, pushed photos become instantly visible inside the Android Gallery app.

DobokuTracker Architecture & Engineering

1. Offline-First IndexedDB Engine & Optimistic Concurrency Control

Construction sites in Japan frequently operate in subterranean excavations, mountainous slopes, and tunnels where 4G/5G connections drop completely. Standard web applications cause catastrophic loss of unsaved daily report inputs in these conditions.

DobokuTracker solves this with a two-tier persistence architecture: all form mutations and worker rosters write immediately to browser IndexedDB before attempting network dispatch. To prevent race conditions when multiple supervisors sync offline drafts simultaneously, the database schema implements Optimistic Concurrency Control with integer version checking. Conflicting updates return HTTP 409 Conflict, triggering an in-app visual diff comparison without discarding the foreman's inputs. Network dispatches use an X-Idempotency-Key mutex queue with exponential backoff to eliminate duplicate records during packet drops.

2. HTML5 Canvas MLIT Digital Kokuban (電子黒板) Engine

Japan's Ministry of Land, Infrastructure, Transport and Tourism (MLIT / 国土交通省) enforces strict inspection photo guidelines: every photographic proof of work must clearly display an inspection chalkboard with project title (工事件名), trade (工種), stationing (測点 STA), and contractor identity. Carrying physical wooden chalkboards and tripods into muddy trenches slows down surveying teams.

DobokuTracker embeds a client-side HTML5 Canvas overlay engine. Before photos are compressed and uploaded, it programmatically renders a timber-framed green blackboard directly onto the image raster. The overlay dynamically paints crisp chalk-white lettering (#F8FAFC) with subtle drop shadows for high legibility, completely eliminating the need for physical chalkboards on site.

3. 3-Tier Digital Hanko (電子印鑑) & Separation of Duties

Japanese corporate culture and legal compliance require hierarchical vermilion seals on field approvals. DobokuTracker implements dynamic SVG/Canvas red Hanko stamps with family kanji, inspection dates, and slight rotational variations mimicking real physical impressions across a strict 3-tier hierarchy: 【担当・職長】, 【現場代理人】, and 【所長・確認】.

To prevent payroll fraud and ensure governance, the backend state machine strictly enforces Separation of Duties: reports created by a user cannot be self-approved by the same user. Once marked as APPROVED, report records are cryptographically locked and immutable.

4. Corporate Reporting Engine (ExcelJS & Zero-Mojibake UTF-8 BOM CSV)

At month-end closing, administrative personnel previously spent 2–3 days copying paper logs into accounting spreadsheets. DobokuTracker automates this using ExcelJS to generate official .xlsx workbooks styled with corporate teal palette (#0F766E), Meiryo typography, auto-computed formula sums, and Japanese accounting double underlines.

For payroll ERP ingestion, the system outputs CSV files with a prepended UTF-8 Byte Order Mark (\uFEFF). This eliminates the pervasive character corruption (mojibake) that plagues standard UTF-8 CSVs opened in Microsoft Excel on Japanese Windows machines.

DroidMirror Studio Architecture

1. Asynchronous Architecture & The Qt Event Loop

In a desktop companion app, calling blocking subprocesses (such as subprocess.run(["adb", "shell", ...])) directly on the main UI thread causes the entire window to freeze, presenting "Not Responding" whenever a device takes longer than 200ms to respond.

DroidMirror Studio implements an asynchronous worker architecture utilizing Qt's QThread and signal-slot system. Each background task (package enumeration, logcat streaming, file pushing) runs in an isolated worker thread. Communication with the user interface is conducted strictly through strongly typed Qt signals, guaranteeing 60 FPS GUI responsiveness at all times.

2. High-DPI Windows Coordinate Mapping

Modern Windows displays utilize fractional scaling factors (125%, 150%, 175%). When launching external native application surfaces like scrcpy via standard Win32 MoveWindow, passing raw logical Qt points caused the window to appear quartered or positioned outside visual boundaries.

The solution was calculating physical device pixels directly via window.devicePixelRatioF() and executing Win32 SetWindowPos with the SWP_FRAMECHANGED flag. This forces SDL to recalculate its internal viewport dimensions, ensuring crisp, unscaled rendering on high-resolution displays.

3. Android Scoped Storage & Intent Synchronization

Starting with Android 10 (API level 29), direct file system operations via ADB often place assets outside the reach of the media provider. Pushed photographs placed into /sdcard/Download/ routinely went unnoticed by gallery applications, requiring developers to manually reboot the phone to test photo-picker features.

DroidMirror Studio solves this by inspecting file MIME types during drag-and-drop operations:

  • Images (.png, .jpg, .webp) are routed to /sdcard/Pictures/.
  • Videos (.mp4, .mkv) are routed to /sdcard/Movies/.
  • APKs and general documents are routed to /sdcard/Download/.

Immediately upon transfer completion, the app broadcasts a system intent:
am broadcast -a android.intent.action.MEDIA_SCANNER_SCAN_FILE -d "file://<path>"
and fires a device notification using cmd notification post to alert the user with sound and banner.

4. Logcat Fatal Exception Accumulator

Standard ADB logcat produces thousands of lines per second, making manual bug isolation tedious. DroidMirror Studio implements a multi-line accumulator thread that monitors the stream in real time. When signature patterns (such as FATAL EXCEPTION or AndroidRuntime) are parsed, it isolates the contiguous stacktrace, illuminates a high-contrast visual alert badge, and populates a dedicated text buffer with a 1-click clipboard export button.
